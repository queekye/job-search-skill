# Optional one-time-code sources

0.1.0 implements a Gotify **client reading token** source. SmsForwarder sends to Gotify with its separate application token; an application sending token is not a reader token. Configure the reader only in the local settings page. This project does not configure the phone, reverse proxy, certificates, remote server or source retention.

首次配置时，Gotify 服务地址和 Token 都要填写。`127.0.0.1` 仅表示正在运行本服务的电脑本机；它不代表已经登录 Gotify，也不免除 Gotify 的消息读取认证。只有 Gotify 确实运行在这台电脑上，才能填写它的实际本机地址和端口。求职工作台默认使用的 `8766` 是工作台端口，不是预设的 Gotify 端口。工作台不会因为填入一个地址就安装或启动 Gotify。

1. 用浏览器打开实际部署的 Gotify 管理网页并登录；本机部署填写实际 HTTP 地址，远程部署填写 HTTPS 地址。
2. 进入 Gotify 的 **Clients（客户端）**，为此工作台创建一个客户端，复制它的 **Client Token**。
3. 回到工作台的“自动验证码”，选择“SmsForwarder → Gotify”，填写 Gotify 服务根地址，并将 Client Token 粘贴到“Gotify 客户端读取 Token”后保存。
4. 页面显示“Token 已加密保存”后，输入框清空是正常现象；同一服务地址再次保存时，可以留空保留。首次配置或更换地址时不能留空。

手机 SmsForwarder 使用 Gotify **Applications（应用）** 中的 Application Token 向服务器发送短信转发消息；工作台使用 Clients 中的 Client Token 从服务器读取消息，两者用途不同。Client Token 不是短信验证码，也不是 Gotify 登录密码。Gotify 客户端令牌还可用于管理客户端、应用和消息，不能将其理解为服务器提供的只读权限令牌；本项目只调用消息读取接口。令牌类型及用途见 [Gotify 官方介绍](https://gotify.net/docs/) 和 [Gotify 官方 API 文档](https://gotify.net/api-docs)。

Windows encrypts the reader token with CurrentUser DPAPI in the private data directory. Normal queries never return it. No token is accepted through the Codex MCP configuration tool. HTTP is accepted only for literal loopback hosts; other configured sources need HTTPS. Redirects are refused and tokens use an HTTP header.

The `otp.configure` operation stores the selected source locally; it does not itself test the server or prove that automatic login works. After saving Gotify and reading the saved source back, the settings page automatically runs the separate `otp.test` check. The “测试已保存来源” button retries that saved configuration without requiring the token to be entered again. For the same Gotify address, leaving the token blank retains its encrypted value (a trailing slash does not change the address). Changing the server requires a new client reading token. Selecting manual input removes the saved Gotify address and token. A failed validation or token-encryption attempt preserves the previous configuration. Windows tests exercise real DPAPI with synthetic tokens in a temporary directory and verify that a new process can read the saved configuration; they do not access existing user credentials.

`otp.test {}` is available only to the local user interface (`actor=user`) and uses the saved, enabled Gotify configuration. It makes one read-only `GET /message?limit=1` request with the token in `X-Gotify-Key`, normal HTTPS certificate verification, no environment proxy and no redirects. An empty inbox is sufficient. The bounded response is checked in memory for the Gotify message-list shape; the test does not extract or return any message text, OTP or Token, send SMS/messages, request a website code, or create/consume an OTP window. It does not change the saved source. A passing result proves only that this Gotify message-read request succeeded, not that phone forwarding or recruiting-site login works.

The result is `{provider:'gotify',status:'passed'|'failed',checked_at,code,message,live_login_verified:false}`. Expected connection failures return a normal result with `status:'failed'`; they do not mean saving failed. Codes distinguish `otp_unauthorized` (401), `otp_forbidden` (403), `otp_timeout`, `otp_unreachable`, `otp_invalid_response`, `otp_redirect_blocked`, `otp_tls_error`, `otp_source_error`, and `secret_unavailable`; success uses `otp_test_passed`. Messages are fixed local explanations and do not copy remote error bodies. Invalid arguments, non-user callers, or a missing/disabled Gotify configuration still return operation errors.

`otp.status.connection_test` is the last completed result for the current configuration, or `null` when none matches. Only its time, fixed result code and configuration digest are stored in the private SQLite `otp_connection_tests` table. Configuration changes hide earlier results. If configuration changes during a test, the test returns `otp_source_changed` and discards that result; delayed older results cannot replace a newer result for the same configuration. Network waits hold neither the module lock nor a database transaction, so status reads and source changes can complete while a test is running. Synthetic tests cover HTTP success, failures, redirects, redaction, persistence, unchanged OTP windows and concurrent configuration changes; they do not access a user's real message source.

Before requesting a website code, call otp.begin with the exact verified HTTPS origin and the company/service label expected in the message. A message-ID baseline is captured. Request one code using the company adapter, then otp.poll with window_id. Only a new message matching the service and OTP pattern within 180 seconds may return a single code. Ambiguity closes the window; consumption cannot be replayed. Cancel with otp.cancel before starting a different service. Source timestamps are reception evidence, not proof that a delayed phone message was newly issued; validate the service message and stop on uncertainty. Window metadata, baseline IDs and the configuration digest live in private SQLite so HTTP and MCP processes share one active window and consume it atomically. Reconfiguration invalidates pending windows; restarting a process does not reset consumption.

The returned OTP necessarily enters the calling Codex tool context in this initial release; the program does not persist raw SMS bodies or OTPs. Gotify/SmsForwarder and the host may retain their own records. A future local field-reference bridge can avoid model exposure. No unrelated inbox reader is exposed.

KDE Connect and Phone Link appear as unavailable integration directions until their adapters and current environment are verified. No silent fallback. Synthetic tests verify baseline, service matching, expiry, ambiguity, one-time use and redaction. A working phone-to-Gotify route is separate from live recruiting-login acceptance.
