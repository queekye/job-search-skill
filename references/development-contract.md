# Development contract v1

This file is the shared implementation contract for 0.2.x. Product: a local applicant UI and independent autofill runtime, one optional Codex plugin, versioned company resource packs, optional OTP and host-managed daily checking. The core version is published in .codex-plugin/plugin.json and service.app.VERSION.

## Ownership and stable resources

Root maintains web/, scripts/, manifest, README, release packaging and integration. Service agent owns service/app.py, service/http.py, service/storage.py (or fewer modules), tests/test_service.py and schemas/profile.schema.json. Company agent owns companies/, service/packages.py, scripts/browser-session.mjs, references/company-pack.md, skills/career/, tests/test_packages.py and schemas/company-pack.schema.json. OTP/MCP agent owns service/otp.py, service/mcp.py, tests/test_otp.py, tests/test_mcp.py and references/otp.md. Do not edit other owners' files without agreement.

Python 3.11+ stdlib runtime; prefer Codex's bundled Python and Git Bash. pypdf is optional for text-layer PDFs. No mandatory Node/npm frontend build. Web is HTML/CSS/JS served by local Python. Keep all new text UTF-8. Source files stay in this repository. Personal data defaults to Path.home()/'.job-search-skill'; JOB_SEARCH_DATA_DIR overrides it. Cache uses LOCALAPPDATA/Codex/tmp/job-search-skill (tempfile fallback). Never download cloud placeholders to audit storage. Do not read/decrypt existing credentials for tests.

## Database and account scope

One shared SQLite database at base_data_dir/career.db is authoritative for accounts, records, per-account settings, tasks, modification history, document metadata and import identities. Structured object fields may use JSON inside database columns; portable JSON exports and old workspace files are not live data sources. Attachments, accepted company packages and encrypted OTP configuration remain managed files outside the repository. Default-account files retain their existing base paths; additional accounts use base_data_dir/accounts/<account-id>. Account isolation applies to module state, OTP windows and connection-test results as well as applicant records.

Database schema version 2 uses PRAGMA user_version. On an existing single-account database, transactional migration binds legacy records, history, documents, settings and import identities to account id 'default', preserving revisions, source evidence, timestamps and document paths. Migration is not a private-profile synchronization or reset. New accounts have independent settings and empty applicant/task data. Account IDs are stable, generated identifiers; names are display labels. Every query and mutation uses the bound user_id, including lookup by an otherwise valid record/task/document/event id.

These are local account profiles under one trusted OS user. They do not implement remote signup, passwords, tenant authentication or authorization across untrusted clients. HTTP remains bound to loopback. A web-session account switch does not change an MCP process's startup binding or a scheduled task's explicit account.

## Shared Python interface

service.app.App(data_dir=None, root_dir=None, user_id='default').execute(operation: str, args: dict | None = None, actor: str = 'user', user_id: str | None = None) returns JSON-serializable data (unwrapped). App exposes base_data_dir (shared database directory, Path), data_dir (bound account's managed file directory, Path), root_dir (Path), user_id and for_user(user_id), which returns a scoped App for an existing account. Omitted execute user_id uses the instance binding; no global "current user" is persisted. Selecting an unknown account fails without creating it. Do not depend on a global database connection across threads. App must work with multiple instances and processes against one DB. service.app.AppError(code,message,status=400) exposes those attributes. Expected errors must never contain user values or raw OS exception details.

Module dispatch: service.packages.execute(app, operation, args, actor) handles resource.*; service.otp.execute(app, operation, args, actor) handles otp.*; service.sync.execute handles sync.*; service.forms.execute handles fill.* and browser.*. App lazily imports these modules. Services can use app.data_dir and app.root_dir. Modules may raise AppError. App.execute rejects unknown operations. All local DB/file operations share service.locking.gate(base_data_dir), including initialization, scoped views and HTTP document byte reads; it is reentrant across threads and uses a crash-released OS lock across processes. Browser commands use short gates around database work and release them before network or browser waits.

## Independent autofill

See [automation](automation.md) for browser/fill operation payloads and [resource authoring](company-resource.md) for the public `form.json` contract and `resource.template/resource.validate`. The eight native tools include `career_forms`. Browser execution is independent of Codex/CUA and shares one local broker between HTTP and MCP processes. Runtime dependencies, dedicated browser profiles and broker credentials stay in the machine-local cache; neither company packages nor private WebDAV snapshots include them.

Prepared company inputs, explicit company answers, selected record IDs/revisions and results live in `tasks.data.autofill`, `kind=prepare`; they remain private SQLite business data and synchronize with tasks. Reserved autofill tasks are maintained through fill operations rather than generic `task.save`. Preparation never establishes job selection or application submission. A run rechecks the current account, selected records, managed documents, package digest and synchronization writer before executing. Public adapters receive only the selected input and managed attachment paths; they are reviewed trusted code, not a JavaScript sandbox.

## Recommendation exclusion feedback

`recommendation.exclude {id,revision,scope:'job'|'company',reason?:string}` is an applicant-only action that removes unsubmitted or unverified recommendations and records durable feedback. `id` is the recommendation record id and `revision` must equal its freshly read revision; `reason` defaults to empty text and preserves the applicant's wording, up to 2000 characters. Eligible stored stages are candidate, legacy preparing/profile_saved, unknown and null/missing stage. Actual application stages and closed history are never archived by this action, even when the same company/job is excluded. Return `{exclusion,removed:[full record snapshots],already_excluded:bool}`. Deletion is a soft archive with incremented record revisions and history, preserving every fact, source, original website status, scope and check time. Matching recommendation records are removed together. A retry using an old revision conflicts; a fresh read of an already archived recommendation covered by the same active scope returns its existing rule without overwriting its reason or creating another rule.

`recommendation.exclusions {include_inactive?:false,limit?:200,offset?:0}` is read-only for applicants and Codex; return `{items,total,limit,offset,next_offset}`, with a maximum page size of 200. Each item is `{id,scope,company,title,job_id,url,reason,identity,active,revision,created_at,updated_at,record_ids}`. `state.recommendation_exclusions` and `task.context.recommendation_exclusions` expose the first 200 active rules in the same format. Every discovery/recommendation run must finish reading active rules through `recommendation.exclusions` until `next_offset` is null. The eight-tool MCP surface exposes this read through `career_get`; it exposes neither exclusion creation nor restoration. Reasons are preference feedback for assessing similar responsibilities, not permission to expand a job rule into a whole company or to exclude a whole direction without the applicant's instruction.

Identity is `{company_key,job_keys,fallback:{title,city,program}}`. Company names use Unicode NFKC, case folding and whitespace normalization only; do not merge legal entities, headquarters, institutes and subsidiaries by stripping name suffixes. Job scope matches the same public job-detail URL independently of company display aliases; URL normalization retains the employer tenant/path and job identity while removing tracking parameters and normalizing query order and origin casing. A bare observed job identifier still requires the same normalized company, so identical numerical ids at different employers do not match. UUID casing is normalized; identifier leading zeros remain significant. Resume/application/account identifiers such as `ResumeID`, `CtmID` and `userId`, and resume/login/list routes, are never used to infer a job identity. Without a stable job id/detail link, the exact normalized title/city/program combination and company are used; missing city/program remain unknown and do not match another city/cohort. Company scope applies only to the matching normalized hiring-company name; sharing one job URL does not broaden company scope. If an employer changes its displayed legal name, verify the alias rather than silently broadening an existing company rule.

Active rules are enforced inside recommendation `record.save`, `profile.import` and `history.undo`, under the same account and transaction as the record operation, covering the legacy unsubmitted and unverified stages above. Direct saving or undoing a matching recommendation fails with `recommendation_excluded` (409). A mixed portable import skips matching recommendations, retaining other records and returning an additive `excluded` count within `skipped`; excluded import identities are not claimed as successful imports. Actual application evidence and closed history can still be stored, since exclusion of recommendations does not erase or forbid actual application records. Codex cannot create/deactivate applicant rules; enforcing an already-existing rule on legacy recommendations reuses its original rule id and audit action without impersonating the applicant.

`recommendation.restore {id:<exclusion-id>,revision}` is applicant-only and requires the rule's current revision. It deactivates that rule and returns `{exclusion,restored:[full record snapshots],remaining_exclusions:[active rule ids],remaining_active_companies:[company keys]}`. `exclusion.active` becomes false and its revision advances. Recommendations, including legacy draft/unknown stages, are restored only when they were archived by exclusion, their record revision is unchanged since that archive, and no active rule or actual company application still suppresses them. Stored stage and all source facts remain unchanged. An unrelated archive or subsequent record change is never undone. With overlapping job/company rules, recommendations deferred by the first restoration are restored when the last blocking rule is deactivated and their company has no actual active application. The rule and record histories remain available; deactivation does not modify official website records or create application evidence.

Exclusions use reserved `kind='custom'` tasks with `instructions='internal:recommendation-exclusion:v1'` and `data.recommendation_exclusion` in the existing private database. Active rules have status completed and inactive rules cancelled; these are internal storage values, not user workflow tasks. `task.list` filters them from ordinary tasks/counts, and generic `task.save` cannot create or change their reserved namespace. Rules, reasons and audit events therefore retain account isolation and survive whole-directory backup/restore and personal snapshots without changing schema version 2. Mutations use the common cross-process gate, SQLite transaction, synchronization writer guard and fresh revisions; no browser profile, credential, personal data file or public fixture is involved.

## Companies with active workflows

An unarchived actual application in stage `user_reported`, `submitted`, `interview`, `assessment` or `offer` suppresses recommendations at the same hiring company. PRE_SUBMISSION_STAGES is `{candidate,preparing,profile_saved}`: the latter two remain accepted legacy storage values but are displayed and guarded as recommendations, never as actual applications. Unknown and null/missing stage also remain unverified recommendations. These recommendation stages, closed history, archived records and a missing company do not establish active company membership. Do not infer submission from raw_status wording, checked_at, login, filling or an attachment. An actual submitted application whose detailed website process is unknown uses submitted with its raw website status, or user_reported when only the applicant reported it; unknown alone provides no submission evidence. Matching uses NFKC, spacing and case normalization, plus the explicitly verified same-employer aliases `阶跃星辰`, `阶跃StepFun` and `StepFun`. Do not strip suffixes, infer parent-group membership or merge distinct research institutes/subsidiaries that share a recruiting portal. Manual exclusion identity remains independent and retains its stricter company-scope rules. No bulk stage migration or new preparation display state is introduced.

`recommendation.activity {limit?:200,offset?:0}` is read-only for applicants and Codex and returns `{items,total,limit,offset,next_offset,suppressed_candidates,suppressed_recommendations}`. Each item is `{company,company_key,record_ids,stages}`; record_ids includes all actual active application records in that account/company and stages contains their distinct active stages. total counts actual active company groups. suppressed_candidates retains the count of unarchived recommendations hidden by actual company activity; it includes legacy draft/unknown recommendation stages. suppressed_recommendations is the distinct union of unarchived recommendations hidden by actual activity or an existing applicant exclusion rule. A record matching both contributes once to this union. Both counts cover the whole bound account, not the current page or historical removals. Manual rules do not appear in items or establish actual company activity. `state.recommendation_activity` and `task.context.recommendation_activity` return the first 200 groups in this format. Discovery must read remaining pages until next_offset is null. Read views (`state`, `record.list`, `task.context`, `recommendation.activity` and account-scoped reads through `for_user`) filter recommendations without changing their stored stages, revisions or histories.

Saving/importing an actual active application or undoing history to one soft-archives matching company recommendations in the same SQLite transaction and OS gate, including legacy preparing/profile_saved and unknown/null/missing stages. Each archive preserves data, metadata and official status/check times, increments revision, and records action `recommendation.company_active:<one-actual-active-record-id>`. Actual applications and closed history are preserved; no permanent exclusion task is created. Recommendation `record.save` and `history.undo` reject an active-company match with `recommendation_company_active` (409). When changing an existing application back to a recommendation stage, the guard ignores that same record and still considers other actual active records and manual exclusions. A mixed `profile.import` skips suppressed recommendations, returns additive `suppressed` within skipped, and does not claim their import identities; both existing actual activity and new eligible actual activity anywhere in that same import batch are considered regardless of input order. Existing source-identity deduplication still applies: a later duplicate active snapshot cannot establish company activity when an earlier closed snapshot consumes its source identity. Manually excluded recommendations count toward excluded first.

`recommendation.reconcile {}` is a writer-guarded mutation available to applicants and Codex, returning `{removed:[full archived record snapshots],total_removed,active_companies:[group objects]}`. It persists cleanup for legacy recommendations suppressed by actual activity or existing applicant rules and is idempotent. For an existing rule, use audit action `recommendation.exclude:<existing-rule-id>` with the actual operation actor; do not create a new rule, change its reason/revision or impersonate actor=user. Manual-rule suppression takes precedence for a record matching both, allowing the existing exclusion restoration history to remain accurate. App startup also performs this cleanup for its bound account only when the local/verified sync writer can write; successful sync writer-state transitions may invoke the same guarded cleanup. Reader/conflict/uninitialized devices and denied ownership checks retain storage while all read views continue filtering. Closing or archiving the last actual active application removes current company suppression for future discovery, but does not automatically restore previously archived recommendations. Recommendation restoration via history or manual-rule restoration remains explicit and guarded. Permanent applicant exclusions remain active until the applicant restores them; application closure never cancels them.

## Whole-directory migration

scripts/run.py backup --output <ZIP> [--data-dir <shared-base>] and restore --archive <ZIP> [--data-dir <shared-base>] run offline; defaults match App. Backup uses SQLite's snapshot API and includes all accounts, records (including archived), histories, settings, tasks, import identities, managed attachments, accepted company packs/receipts and pending package review data. Relative member paths and hashes permit relocation without changing business IDs, source evidence, nulls or official check times. Pending executable packages remain pending. Portable profile JSON is not a complete backup.

Restore accepts a new or empty private target only. Validate schema, members, hashes and document references before installing the staged directory; never merge, replace an existing database or run restored packages. In the restored copy, running tasks become pending with a revision increment and audit event; completed/cancelled tasks stay unchanged. Disable host scheduling and remove host_task_id/allow_relogin, incrementing changed settings revisions. Clear transient OTP windows/connection tests and protected tokens; preserve provider/address disabled so the applicant can reconnect. Browser logins and external automation are not portable. Historical paths remain evidence; current managed document paths come from document.resolve. No bulk restore HTTP or MCP action. See [migration instructions](migration.md) for handoff and private archive handling.

## Personal synchronization

`sync.status {}` returns `{configured,config:{url,username,workspace,automatic,password_set},device_id,mode,dirty,last_synced_at,last_error,remote_owner}`. It is global to the shared base directory, not the web-selected account. `state.sync` and `task.context.sync` expose the same redacted status; `career_get` can read sync.status without adding another native tool. Modes are local/uninitialized/writer/reader/conflict. Configured read-only, uninitialized or conflicting devices must not continue workflow writes or bypass the service.

User-only `sync.configure {url,username,password?,workspace,automatic}` saves local DPAPI-protected credentials, never returns the password, and resets remote capability checks. Empty/omitted password retains it only for the same URL, username and workspace. `sync.run {}`, `sync.handoff {}` and explicit `sync.takeover {}` exchange personal snapshots with an HTTPS WebDAV directory (loopback HTTP only for synthetic tests). Background workers in HTTP and MCP check automatic configuration every 30 seconds. Closing both stops synchronization. No two-writer or offline merge; configured business writes verify current owner and head online, while local OTP and machine-only schedule bindings remain available independently.

User-only `sync.disable {}` stops synchronization and online ownership checks, retaining local data, protected configuration and ancestry. It returns status plus `changed:true` so the web UI reloads its workflow state. Re-enabling the same configuration reuses the device identity and baseline and checks unsent local edits against the remote head; it never treats disabling as an uploaded handoff.

Snapshot scope personal-sync contains the complete shared database and all DB-managed document originals only. Company packages/receipts/review/locks are public resources, not synchronized. OTP configuration/tables, WebDAV credentials/cursors, browser sessions and enabled/host_task_id/allow_relogin are machine-local. Desired schedule time/timezone and preferences synchronize. New writer acquisition resumes old running tasks as pending with history, including recovery if ownership publication was interrupted.

WebDAV requires strong ETags and verified conditional creation/update. Immutable ZIP uploads precede a conditional latest.json commit; unknown workspace, unsent branch, corruption or a failed CAS preserves existing local data. A fresh empty device can pull an existing workspace; an unrelated populated local directory is not overwritten. New snapshot application uses a validated stage, stable parent OS gate, recoverable directory-swap journal and one local previous copy. Public resources and other local files survive the swap. Normal remote retention is five snapshots; failed deletion/publish can leave extras. The transport is HTTPS, snapshots are not end-to-end encrypted. See [sync instructions](sync.md).

## Record data fields used by UI

basic: name,email,phone,location,summary. education: school,degree,major,department,start_date,end_date,description. experience: title,organization,role,start_date,end_date,description,category (project/work/research/publication/skill/award). family: relation,name,organization,department,role,employment_status,confirmed_at,notes. preference: category (cities/roles/industries/excluded/other),value,notes. application: company,title,url,city,program,job_id,application_id,recommendation_bucket (recommended/exploratory/pending/excluded),fit_tier (A/B/C),recommendation_scope,stage (candidate/preparing/profile_saved/user_reported/submitted/interview/assessment/offer/closed/unknown),raw_status,checked_at,last_attempt_at,coverage (complete/partial/unknown),next_action,blocker,decision,evidence_url,notes. Dates month or ISO strings, null for unknown. External website state is never modified by editing local records.

Job discovery defaults to formal campus recruitment. Internship search and recommendations require an explicit applicant request within the current scope; the latest scope decision takes precedence. Recommendations are presented in a separate "推荐岗位" area and excluded from "投递情况" and submission counts until actual application evidence exists. Applicant-selected form preparation remains in recommendations; the task/history can retain form progress without inventing an application. Existing candidate/preparing/profile_saved storage stages remain compatible, but new local preparation does not require a separate display status or a new preparing-stage record. Unknown and null/missing stages remain unverified recommendations. Only an actual application established by an applicant report or official evidence is shown as an application (user_reported or officially verified submitted according to the evidence). Login, company-resume editing, fill authorization, a suitability assessment and raw-status keywords are not submission evidence. Do not automatically promote records or bulk migrate private stages when applying this presentation rule; preserve original source facts and history.

Application recommendation metadata is optional and additive within portable schema v1. recommendation_bucket accepts recommended/exploratory/pending/excluded or null; fit_tier accepts A/B/C or null; recommendation_scope is text up to 500 characters or null. These fields describe AI analysis for display, never official website status, applicant selection or submission permission. pending means evidence or a condition needs clarification and does not establish that the applicant can apply. A tier applies only to the recorded direction or subdirection; never generalize a subdirection's tier to the whole field or other directions, and retain an unknown scope as unknown. Display ordering uses bucket, then tier, then stable record identity; entries in the same tier remain peers and identity ordering does not indicate a finer priority. Do not infer a group, tier or scope from stage, saving, updated_at or missing evidence. Omitted fields remain omitted, explicit nulls remain null, and imports/exports preserve both without migration or backfilling existing records.

Application continuity fields are optional and additive within portable schema v1: job_id and application_id preserve the website's distinct job and application identifiers as text (up to 500 characters, including leading zeros). next_action and blocker are descriptive text (up to 12000 characters). decision preserves the applicant's own words (up to 500 characters), including a decision to pause or stop; it is not an enum, an instruction to execute, or permission to submit/withdraw. evidence_url is an HTTP(S) link without embedded credentials (up to 2048 characters); unknown values are null. Do not infer these fields from missing evidence, repurpose stage to encode decisions, or automatically migrate existing private records.

checked_at is the last successful observation of the website state within the recorded coverage. last_attempt_at records the latest check attempt, which may be failed or blocked. A failed attempt can update last_attempt_at and blocker but must retain the earlier checked_at, raw_status and stage; an empty/loading page is not a successful status observation. Timestamps are supplied from actual evidence, never automatically advanced by saving or importing a record. Old records without the optional fields remain valid and export unchanged; imports and exports preserve provided values and nulls.

## Company packages operations

resource.list -> {items:[{id,name,version,description,origin,capabilities,verification,installed,installed_version,sha256,source}], registry_configured:bool}. Bundled packages available offline from companies/; installed versions in data_dir/packages/id/version and packages.lock.json.

## OTP operations

otp.status -> redacted configured provider state. otp.configure {provider:'gotify'|'kde'|'manual',url?,token?,enabled?} persists config outside repo; actor=user only; read never returns token. Gotify exact loopback HTTP or HTTPS allowed; do not reconfigure remote server. otp.begin {service,origin,sender_hint?} captures message baseline before website requests code, returns window_id and expires_at. otp.poll {window_id} gets only newer same-service matching OTP; short TTL and one-time consumption, ambiguity returns explicit block. No writes to browser or SMS source. otp.consume? decide in module documentation if poll consumes. Query uses Gotify API with auth headers, never token in URL/log. provider='kde' may report not_implemented until deterministic support, no fake fallback. Tests use stub HTTP and synthetic messages only. SMS source may retain its own history; this app does not persist raw message bodies/OTP.

otp.test {} -> {provider:'gotify',status:'passed'|'failed',checked_at,code,message,live_login_verified:false}, actor=user only. Tests the saved enabled Gotify source using GET /message?limit=1 with the client token in X-Gotify-Key; preserves TLS verification, disables environment proxies and refuses redirects. A valid empty message list passes. No SMS sending, website request, OTP extraction, raw body/token output or persistence, source mutation, or OTP window creation/consumption. Expected network/authentication/response failures return status=failed with fixed redacted messages and specific codes: otp_unauthorized (401), otp_forbidden (403), otp_timeout, otp_unreachable, otp_invalid_response, otp_redirect_blocked, otp_tls_error, otp_source_error, secret_unavailable; success is otp_test_passed. Argument/authorization/unconfigured-source errors remain AppErrors. Saving and testing are distinct operations; a failed test never implies configuration was unsaved.

otp.status additionally returns connection_test (the matching result above or null). Persist only code, checked_at and configuration fingerprint in a separate private SQLite otp_connection_tests table. Compare the current configuration fingerprint under the SQLite write lock before recording a result; a concurrent source change returns otp_source_changed and discards the result. Older completed results cannot overwrite newer checked_at for the same configuration. Network tests hold neither the module lock nor database transactions during network waits. The operation is intentionally absent from Codex MCP tools. Passing a connection test never sets live_login_verified=true.

## Local HTTP

service.http.main supports --data-dir --user-id (default 'default') --port (default 8766) --host 127.0.0.1 only. GET / returns web/index.html, /app.js /styles.css /catalog.html /catalog.js assets. GET /api/accounts returns the local account list for the cookie session. GET /api/state?user_id=<id> -> envelope {ok:true,data:state}; POST /api/action body {operation,args,user_id} -> envelope. HTTP-only account.select {args:{id},user_id:<current-id>} changes this cookie session's account and returns selected account.get; it does not modify an App/MCP startup account or a database-wide active account. Requests carrying a stale account id fail with 409 rather than accessing the newly selected user. Omitted user_id remains compatible for the default session only; nondefault sessions must supply it. Managed document read/download GETs also require the account query when nondefault.

All API requests require a same-site random HttpOnly session cookie obtained when opening root. Mutations additionally require exact same Origin (localhost or 127.0.0.1 with actual port); Host validated, no permissive CORS, no external assets. Set CSP to self (scripts/styles files), no framing, Cache-Control no-store on API/private documents. Limit requests. User-only routes use actor=user, MCP actor=codex. Errors {ok:false,error:{code,message}} with 409 for revision conflicts and stale account requests. Do not bind publicly. Root handles public release packaging separately.
